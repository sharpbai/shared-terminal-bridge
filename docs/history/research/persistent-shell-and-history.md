# 不中断 SSH Shell 与 tmux 历史查看

> 整理日期：2026-10-14。状态：方案调研，尚未部署 ET 或 shpool，未完成 STB 兼容验收。本文是独立专题，不代表已支持的新功能。

## 我想解决的问题

我希望网络切换、短暂断网或电脑休眠之后，继续使用同一个远端 Shell：目录、环境和正在执行的任务不丢。同时，我可以用本机 tmux 查看历史，STB 也能读取足够连续的输出，不再只看到远端终端重绘的当前屏幕。

目前先复用已有项目，不开发专用 SSH 客户端。远端组件必须显式部署，不通过隐藏脚本或自动 bootstrap 偷偷改变目标环境。

## 三种持久性不能混为一谈

| 需求 | 实际含义 | 不意味着什么 |
| --- | --- | --- |
| 持久 Shell | 断线后原 Shell、目录、进程仍存在 | 原网络连接一直没有断 |
| 自动重连 | 网络恢复后续接既有会话 | 自动重新执行断线前的命令 |
| 历史保留与补读 | 已显示和断线期间输出可按需要查看 | 无限保存、永久落盘或权威退出码 |

服务器重启、持久会话服务退出、缓冲溢出和客户端重启是不同故障。不能用“支持断线重连”概括所有恢复保证。

## 现有 mosh 层级与滚动问题

本次只读核对 `lisa-lax9929-1` 时，本机 STB 托管 pane 的前台程序为 `mosh-client`，屏幕停在远端 root Shell 提示符。可以确认的结构为：

```text
本机 Terminal → 本机 STB / tmux → mosh-client → 远端终端
```

仅凭屏幕没有状态栏，不能排除远端还有隐藏状态栏的 tmux；本次未在远端输入探测命令。历史会话名和 pane ID 不作为后续操作的固定参数。

mosh 同步可见屏幕状态，可以跳过中间画面，不保证把所有应用输出送到本机。外层 tmux 保存的是接收到的渲染内容，不能恢复从未收到的输出。这是滚动历史不完整的机制性原因，而不是单纯历史行数不足。[mosh 官方说明](https://mosh.org/#techinfo)

给 mosh 增加远端 tmux，能够保存远端历史并改善人工查看，但不会自动让外层 STB 获取全部历史。

## 方案比较

| 方案 | 网络中断与 Shell | 人工历史查看 | STB 读取 | 部署代价与限制 |
| --- | --- | --- | --- | --- |
| SSH + 远端 tmux | Shell 保留，重新登录并 attach | 远端 tmux 保存历史 | 外层主要看到内层 tmux 渲染；完整历史需另行显式读取 | 安装远端 tmux，无新网络协议 |
| mosh + 远端 tmux | mosh 处理网络变化，tmux 保留 Shell | 在远端复制模式查看 | 仍是屏幕同步，外层输出可能不完整 | 两端 mosh、远端 tmux及 UDP 可达 |
| Eternal Terminal（ET） | 自动续接既有会话 | 连续字节流有利于本机 scrollback | 最值得直接试验，尚未验证 | 两端安装，远端服务与额外 TCP 端口 |
| SSH + shpool | 远端 Shell 保留；SSH 断后重新 attach | 正常连接保留原生历史，重连恢复最近 N 行 | 适合现有 SSH 通道；恢复重复与截断需验证 | 远端安装 shpool，不新增网络端口 |
| ssh-obi | 普通 SSH 自动重连、持久会话 | 有界回放可能重复 | 回放语义与隐式 bootstrap 不符合默认边界 | 需明确关闭或替代自动安装，并进一步审查 |
| zmosh | 项目提供持久会话及 UDP 重连 | 项目提供历史导出 | 有潜力，但尚未评估成熟度与兼容性 | 新的远端组件与协议，不作为首选 |

ET 和 shpool 的 STB 适合程度是根据输出路径作出的推断，不是实测结论。正常 Shell 输出与全屏 TUI 重绘也需要分别验证。

## 优先候选一：Eternal Terminal

建议试验的结构：

```text
本机 STB 托管 tmux → ET → 远端 Shell
```

ET 先借助 SSH 建立会话，随后使用可恢复的连接。它按字节序号补传，而不是只同步最新屏幕，适合观察“本机历史是否能连续保存”。服务端默认 TCP 2022，必须核对防火墙与访问范围；macOS 官方说明提供 MacPorts 安装方式。[项目说明](https://github.com/MisterTea/EternalTerminal)、[恢复机制](https://eternalterminal.dev/howitworks/)

不要为了持久化先叠加远端 tmux：内层重绘可能重新引入当前的问题。若还要远端多窗口或客户端退出后的持久会话，单独核对所用版本的保证。

重点限制：

- 缓冲有界，字节补传不是永久审计或无限历史。
- 断线期间的输入可能已进入传输缓存；本地撤权不一定能撤回已经送出的字节。
- 开发分支 README 的能力不能直接视为已安装发布包的能力。使用前核对客户端、服务端版本及命令帮助。
- 程序化 `etctl run` 的自动 framing 可使用 wrapper 或 echo marker，不能直接替换 STB 的可见命令提交路径。这里只考虑复用交互传输，不采用其隐式命令包装。[开发分支接口说明](https://github.com/MisterTea/EternalTerminal#programmatic-control-etctl)

## 优先候选二：SSH + shpool

建议试验的结构：

```text
本机 STB 托管 tmux → 普通 SSH → shpool → 持久 Shell
```

shpool 保管命名 Shell，正常连接直接转发输出，不持续接管整个终端画面；客户端不需要增加软件。重新 SSH 后 attach 同名会话，可以返回原 Shell。它本身不是 SSH 自动重连工具。[官方 README](https://github.com/shell-pool/shpool)

需要显式配置并验证：

- 默认恢复一屏；需要更多上下文时使用 `session_restore_mode = { lines = N }`，并核对输出缓冲上限。
- 不采用 `simple` 恢复模式来满足完整历史需求，它不补回断线期间的输出。
- 设置 `prompt_prefix = ""`，关闭默认提示符前缀注入，避免无必要改变目标 Shell 提示符。
- 不默认强制踢掉另一个人工客户端，不因自动重连而抢占他人的会话。

这些配置是显式准备目标环境的一部分，不由 STB 暗中执行。[恢复与提示符配置](https://github.com/shell-pool/shpool/blob/master/CONFIG.md)

shpool 更适合额外端口受限、已有 SSH/堡垒机必须保留的环境。断线后输出恢复仍是有界的，是否重复、遗漏或重绘，需要实际测试。

## 其他候选的取舍

[ssh-obi](https://github.com/menhera-org/ssh-obi) 使用普通 SSH，但文档明确允许重复回放、只有有界近期缓冲，并包含自动 bootstrap。暂不直接采用其默认流程。

[zmosh](https://github.com/mmonad/zmosh) 提供会话持久化、重连和历史命令。其能力描述来自项目文档，尚未完成安全、版本和故障验收；名称相似不表示它与 mosh 协议兼容。

单独使用自动重启 SSH 的工具，也不能保证返回原 Shell；必须与明确的持久会话机制配合。SSH keepalive 有助于发现死连接，但不能让 TCP 在所有网络变化中保持不断。

## STB 安全与观察边界

STB 继续拥有本地 pane ACL、lease、generation、Human Override 和审计。传输工具不能获得一套绕开这些检查的独立 Agent 写入入口。

1. 断线时不得继续积压新的 Agent 写入；不能只因客户端进程还存在就判定远端可执行。
2. Human Ctrl+C 后，同一用户回合不重新 acquire，不自动恢复旧 generation。
3. 重连不自动重放模型命令；已经交给传输层的字节能否取消，必须单独验证。
4. 历史补传与实时输出应区分；不能把补回的旧提示符当成新任务完成证据。
5. 提示符完成判断是启发式，不是可靠退出码。采用现成传输也不会自动改变这一点。
6. 只读查看历史不申请写入租约；远端历史读取若需要输入命令，仍走正常授权路径。

调研时 STB 的远端进程识别集合尚未包含 `et`，也没有明确的传输断线状态接口。ET 或 shpool 可先用于隔离人工试验，不能直接宣布已经安全支持 Agent 自动操作。必要的小范围 STB 适配，与开发专用客户端是两种不同工作量。

## 下一步验证清单

先使用隔离、明确命名的测试会话，不替换正在使用的运维连接，不执行业务修改命令。

| 验证 | 通过标准 |
| --- | --- |
| 短暂断网、网络切换与电脑休眠 | 恢复同一 Shell；目录、会话内状态和前台任务仍在 |
| 客户端退出与重启 | 明确能否重新接入；不把不同版本或故障的保证混为一谈 |
| 大量连续输出与鼠标查看 | 本机 tmux 历史可读；滚动查看不抢占或误释放写权 |
| 断线期间输出 | 核对序号和缺口；识别重复、截断、缓冲上限 |
| STB read/read_delta | 输出范围有界；补回旧输出不误认为新任务结果 |
| 断网期间 Ctrl+C 与撤权 | 重连后不执行已撤销的待发 Agent 操作；无法保证则限制为人工使用 |
| 任务完成和目录变化 | wait 能结束；重绘、恢复提示符和断线信息不误触发完成 |
| 中文、窗口调整与 TUI 退出 | 显示正常；普通 CLI 与 TUI 分别记录，不承诺 TUI 全自动 |

优先试验 ET；若新增服务或端口受限，改试 SSH + shpool。通过后再决定是否只需要少量 STB 兼容调整。若两者都不能满足执行安全或可靠补读，再评估专用连接层，而不是先重写 SSH/mosh 客户端。

## 当前结论

我暂时不开发新客户端。现成方案已经覆盖持久 Shell、自动重连和原生历史的主要需求，但没有任何方案在本项目中完成三者与 STB 安全边界的联合验收。下一步以隔离实测决定采用哪条路线；本文仅保存调研和验证计划，不表示已经安装或启用。
